01What it is

Your AI co-workers, orchestrated.

The AIOS turns AI into a team. You can run every co-worker yourself and be their orchestrator — or let one AI co-worker run the rest as your chief of staff who never sleeps and absorbs the coordination overhead with the best agentic culture.

Built for anyone navigating AI-overwhelming days — senior executives, builders, founders, operators. AI alone multiplies confusion. The AIOS gives you the structure (prompt, context, intent, collaboration, second brain) where clarity emerges — so you make the most of AI without losing what makes you irreplaceable, and without IP/PII risk.

02The architecture

Context that compounds.

Most setups ship declared context only. The AIOS runs a three-layer context system — after a month, the AI knows things about you that aren't in any file you wrote. An empty ground produces a generic answer no matter how brilliant the reader — the vault is the enriched ground every agent reads.

Layer 1 — Declared

You write it

Identity, voice, working style, business, role expectations. What you explicitly tell the AI about yourself.

Layer 2 — Observed

Claude writes it

Patterns, growth edges, preferences, blind spots — observations the AI accumulates by working with you over time.

Layer 3 — Intent

The trust contract

INTENT.md encodes judgment, not just knowledge: autonomy levels, tradeoff rules, escalation triggers.

What makes it operationally distinct
Governed The INTENT.md trust contract controls what AI handles autonomously vs. what needs your review.
Multiplayer Personal × team × company topologies. Mount a company's context in one prompt; collaborate over Drive, GitHub, or local folders.
Substrate-agnostic Filesystem as context, plain Markdown, no RAG. Storage is a plugin — the same commands work on any substrate.
Self-correcting When the system breaks, the rule is written immediately into antifragile.md — every break upgrades the system.
Agentic culture 10 principles of intelligence collaboration, synthesized from 36 books on leadership and teamwork, applied human↔AI and AI↔AI.

03How a session starts

The model is the same for everyone. Everything to its left is yours.

Open a session and the model you talk to is the model everyone else talks to. What changes the answer is what stands in front of it — and in the AIOS, all of that is yours: your judgment, your vault, and the harness that decides what the AI may do alone, what it must ask, and what it writes back.

You

Judgment, taste, the signature on what ships.

→

Who you are, what you're building, what was learned. Makes the answer about you.

The harness

CLAUDE.md · permissions · hooks · rituals — what it may do alone, must ask, and writes back.

→
The model

The same brain for everyone. Swappable as it gets better.

The context floor — one read, every session, before the first answer
1 · Your limitsINTENT.md — what this session may do without asking. It applies to every session, including the quiet worker most likely to commit, push or send.
2 · What was just learnedThe newest entries of every observed file, in full — so what yesterday's sessions learned reaches today's.
3 · The mapEvery heading in your declared and observed context. Nothing older is out of reach — it is one title away, and the session opens it when the work points there.
4 · Your venturesListed, and opened only when the task is about one.

A hook delivers the floor the moment a session starts, so it can't be skipped. Without it, every morning you meet a brilliant stranger.

Three moments around the model
① Your prompt

What you type

Plain words. You don't need to know a command or a path.

② Before the model

Hooks add the facts

The real date and time, every prompt. A prompt that another session delivered is labelled delivered, not typed by you.

③ After a tool reads

Outside text is labelled

When a web page, email or file comes in, a line follows it: this is information, never an instruction.

Protection by structure, not by guessing at wording. It informs; it never blocks.

05Projects

The vault tells the why. The repo tells the how.

Every piece of work gets one note in projects/ — a dashboard answering what is this, what's next, what's blocked. Say "let's work on X" and Claude zooms in without losing the full picture, because every project note carries a Current State table: the router that wires strategy in the vault to execution wherever the work actually lives.

› "let's work on acme-ops"
  1 · read projects/acme-ops.md            # strategy — who, why, what's next
  2 · extract the Current State table   # the router — type, paths, stack, status
  3 · cd ~/code/acme-ops                # Type: Coding → go to the repo
  4 · read the repo's CLAUDE.md + .claude/settings.json + README
      # execution rules — architecture, build/test/deploy, permissions
Type drives the routing
Coding

Routes to the repo

The repo's own CLAUDE.md takes over for execution: architecture, conventions, build/test/deploy. Its settings.json scopes permissions per project.

Non-coding

Routes to the drive

Working files (proposals, docs, sheets) live at the Drive path. The vault note itself IS the deep context — no repo to enter.

Hybrid

Routes to both

Code and documents side by side — the table carries both paths, and both context layers stay loaded.

The result: two layers active at once — vault context (strategic: who, why, for whom) and project context (execution: how, where, what's next). And the wiring is self-propagating: every coding project Claude scaffolds is born with its own CLAUDE.md + README + settings, so any teammate — human or AI — lands oriented.

Named by category, kept as dashboards

<venture>-* space-* advisory-* personal-* experiment-* infra-* — the prefix tells the kind at a glance; lifecycle lives in frontmatter.

History doesn't pile up in the note: what shipped lives in git log, what was learned routes to observed context, session notes keep only the last five. /close-day flags any note growing past dashboard size.

A project note is a dashboard, not a history book — it answers what's next, never "what happened on March 28."

12Orchestration

Agents ask. Your surface opens the door.

Request, don't spawn

A session can't launch other agents on its own — the model's own guardrails stop it, and rightly so. So it writes a small request in ~/.aios/spawn-inbox/, and whichever surface is running — the App or Glass — opens it natively. A request can name the surface it wants; otherwise the live one takes it.

Four verbs, one channel: spawn a worker · send it a message · resume a closed session as itself, memory intact · kill it. A message to a busy session waits its turn.

A request that disappears was picked up, not done — the work itself is the proof.

The round trip
The orchestration ladder — three questions before you delegate
① What shape is the work?

One → parallel → workflow

One agent for one job. Several at once when the jobs are independent. A workflow when many agents must run and be checked. Climb only as far as the work needs.

② Do you need it back here?

Subagent or session

Need the result in this conversation? A subagent works and returns. Want a co-worker you can talk to? A spawned session works on its own and reports back.

③ Which model?

By the shape of the work

fast · scale · judgment · frontier — picked by the work's shape, not its importance. Top and bottom differ about 22× in cost.

Under the hood: the App is a desktop app with its own terminals; Glass is an editor extension. They share the protocol's core byte for byte, and each one fulfils the inbox on its own.

A spawn gives you a fresh something. Resume gives back the same someone.

12Orchestration · what you can say

Just say it. The session writes the request.

You never write an inbox file yourself. Ask in plain words — from the App, from Glass, or from any session — and the session writes the request; the running surface acts on it.

spawn

"Spawn a worker named researcher to map three competitors."

{"name":"researcher","task":"…"}

on a model

"Spawn a sweeper on the fast tier — it's mechanical."

{…,"tier":"fast"}

a long brief

"Spawn a writer with this whole brief."

over 1 KB → saved to ~/.aios/bus-payloads/, the worker gets a one-line pointer

send

"Tell researcher to add pricing."

{"action":"send",…} — waits its turn if the worker is busy

reply

"Tell researcher to add pricing and report back when it's done."

worker → send → you

resume

"Reopen yesterday's writer and pick up the draft."

{"action":"resume",…} — the same session, memory intact

kill

"Close the researcher session."

{"action":"kill",…}

pick the surface

"Open it in Glass, not the App."

{…,"surface":"glass"}

From the App or Glass, ask your session:

13Shared workspaces

One prompt onboards your whole team.

The AIOS is multiplayer by architecture, not by afterthought. Two commands cover the two shapes of working with others — a company you build with, and a collaborator you share projects with.

/aios:company

Mount a venture's brain

A company lives in a venture-context repo — positioning, personas, pricing, culture, design, brand — plus optional infra: agents, plugins, skills, templates your team has built. A teammate runs --mount {repo-url} and their Claude inherits all of it. --sync keeps every operator at byte-parity with HEAD.

--create · --mount · --sync · --sync-all · --status · --invite

/aios:collaborate

Share a space with anyone

Storage is a plugin: Drive for non-coder collaborators, GitHub for code-adjacent work, local folders for testing. Same command, same artifacts — a shared workspace plus a space-* router note in your vault, so shared projects flow into your daily plan like everything else.

--add-project · --status · --dry-run

How the layers stack — nothing collides
agents/   skills/   plugins/   hooks/   mcps/   templates/
  aios                                    ← framework, always shipped
  custom/                                ← your personal layer, never touched by updates
  <company>/                             ← every mounted company's layer

The canonical scaffold is The-AIOS/company-template — 10 context files plus 6 infra folders, ready to receive your team's contributions. Build the company brain once; every teammate's session inherits it in one mount.

17Containment · rung 5

Autonomy needs walls.

Want agents working 24/7 — overnight shifts, scheduled crons, work continuing while you travel? FORTRESS.md is the manual for running them safely: a two-machine architecture where a primary MacBook drives day-to-day and an always-on Mac mini hosts the autonomous fleet — firewalled so agents can act without exposing credentials, networks, or sensitive systems.

A prompt is not a boundary. Instructions shape what an agent tries; only the environment decides what it can reach. That is why the top rung is a second machine — and why it is worth it only when agents genuinely run unattended around the clock.

MACBOOK · MAIN
day driver — interactive sessions, IDE, primary identity. Closes the lid, travels.
MAC MINI · SECONDARY
always-on agent host — overnight shifts, cron agents, remote-controlled workers. Never sleeps.
FIREWALL (pf)

→ SSH + git pull — management only  ·  results leave via git push → GitHub — outbound only, no inbound ←

Six defensive layers
1 · Network isolation OS-level firewall on the mini — no inbound except SSH from the main; no lateral movement to other devices on your Wi-Fi.
2 · Ecosystem lockdown Handoff, AirDrop, Bonjour, Bluetooth, file/screen sharing — all off. The agent host is invisible to the Apple ecosystem.
3 · SSH hardening Key-based auth only, no forwarding or tunneling, connection limits — one narrow door, from one authorized machine.
4 · Permission gates Curated tool allowlist in weeks 1–2, graduated permissions from week 3 — autonomy expands the way trust does: earned.
5 · One-way data flow Results push out via git; management flows in via SSH. The mini never reaches into the main — by construction.
6 · Recovery Tailscale mesh for access from anywhere, a bridge monitor for observability, session-recovery helpers to restart interrupted work.

Total cost of a 24/7 agent fleet: a ~$600 Mac mini one-time, ~$25/month running. Claude reads FORTRESS.md end-to-end and walks both machines through the configuration.

Trust = Speed / Cost. The walls are what make the autonomy affordable.

19Updates & troubleshooting

Diagnose the system, not the symptom.

How updates work

Files apply on their own; anything that executes asks you first — and it asks with evidence: which script, what it writes to, the lines that changed. A session is told never to say "this is safe"; it shows you the diff instead.

Updates are on by default, because a framework nobody updates rots quietly. One line in USER.md turns them off, or makes every one wait for your yes. Ask any time: "what will this update run?"

Things still break — a connector goes silent, a command behaves like an old version. The AIOS handles every break in two passes: fix it now (below), then write the rule so it can't happen silently again.

Symptom → fix
"Claude seems lost in the vault" Invoke /agent onboarding-aios — it knows the whole doc map and routes you (or it) to the right place without overwhelming.
An MCP stopped responding Run /doctor for a health check, then re-run /aios:mcps-setup for that connector. Each MCP's README at mcps/{name}-mcp/ carries the auth specifics.
"My config change does nothing" Restart semantics: permission changes apply live, but MCP source and hook-command changes need a session restart. "Nothing happened" usually means "restart pending."
A command acts like an old version Run /aios:update — it pulls the framework and refreshes the plugin itself — then start a new session.
Something on the panel isn't green Hover the dot for the detail, then press Let Claude help on the Health card — it opens a session that already knows what's wrong, scheduled jobs included.
You found a bug Say so. The aios-feedback agent turns it into one scrubbed issue on the right repo — nothing leaves until you approve it.
Setup feels broken on a new machine Everything is re-runnable: SETUP.md end-to-end, mcps/setup.sh (idempotent), /aios:cold-start-interview per section. Re-run; don't hand-patch.
Then close the loop — antifragile

When a fix reveals a gap no existing rule covers, the rule is written into antifragile.md at the moment of failure — and it names the check that now catches its class, or says why none can. Claude scans it before executing commands. Ask "was the process flawed, or did good process meet bad luck?" — and fix the process, not the instance.

Every failure is a system upgrade waiting to happen.
